

# 📘 xv6 Lab: copyin/copyinstr (Hard) 实战推演笔记

> 实验目标：将用户页表的地址映射同步到进程的内核页表，使 `copyin_new` 能直接使用指针（硬件翻译），替代原 `copyin` 的软件查表（`walkaddr`）。

---

## 1. 实验本质：我们在“同步”什么？

### ❓ 初遇困惑
一开始看到 `copy_proc_to_kernel`，以为是把用户内存里的数据（比如字符串 `"hello"`）拷贝给内核。

### ✅ 最终理解
**同步的是“映射关系（页表项 PTE）”，不是“内存数据（字节内容）”。**

- **类比**：物理内存是一栋宿舍楼，用户页表是一本地址簿（写着“书桌在 301 室”）。
- 任务是把 301 室这个**房间号**抄到内核的地址簿里。至于 301 室里摆的是书还是电脑（数据），内核根本不管，也不需要拷贝。

### 📌 关键结论
只要物理页框号（PPN）没变，即使里面的数据变了（如变量从 5 改成 10），内核页表也不需要动，因为指针依然指向正确的物理地址。

---

## 2. 为什么原 `copyin` 不能直接用指针，而 `copyin_new` 可以？

### ❓ 困惑点
为什么内核不能直接 `memmove(dst, (void*)srcva, len)`？

### ✅ 原理解析
- **旧方案**：内核页表里**没有**用户进程的虚拟地址映射。直接解引用 `srcva`，MMU 在内核页表里查不到，会触发缺页异常，内核崩溃。
- **旧方案做法**：必须用软件遍历用户页表（`walkaddr`），手动把 `srcva` 翻译成物理地址 `pa`，再用 `memmove` 去读 `pa`。这是“软件翻译”，慢且复杂。
- **新方案**：实验后，内核页表里有了 `srcva -> 物理地址` 的映射。此时 `memmove` 触发硬件 MMU 自动翻译，高效且代码简洁。

---

## 3. 为什么同步范围是 `[oldsz, newsz]`（增量）而不是全量？

### ❓ 困惑点
为什么 `copy_proc_to_kernel` 只循环 `oldsz` 到 `newsz`，而不是从 0 到 `newsz`？

### ✅ 原理解析
- 这是 **“增量更新（Incremental Update）”** 策略，为了性能。
- `[0, oldsz]` 这部分映射在**之前**已经同步过了，且没有变化（物理页框号没变）。
- **只有** `[oldsz, newsz]` 这段是新分配的物理页（比如 `sbrk` 刚申请的堆），用户页表里刚建好映射，内核页表里还没有。
- **结论**：只复制增量差值是高效的，不是偷懒，而是精准的优化。

---

## 4. ⚠️ 重要发现：实验代码的“缩容漏洞”（悬空映射）

### ❓ 质疑点
如果进程缩容（`sbrk(-4096)`），物理页被 `kfree` 释放了，但 `copy_proc_to_kernel` 在 `newsz < oldsz` 时循环直接跳过，**内核页表里残留的映射怎么办？**

### ✅ 后果分析
- 内核页表依然指向那块已被释放的物理页，形成 **“悬空映射（Dangling Mapping）”**。
- 如果恶意程序向内核传入已释放的地址，`copyin_new` 会通过残留映射读到已经重新分配给其他进程的敏感数据（信息泄露漏洞）。
- `usertests` 能通过是因为它缩容后不会主动去访问已释放的区域，但这在安全上是严重缺陷。

### 🛠️ 正确修复（可选，但强烈推荐）
在 `growproc` 的缩容分支中，手动清除内核页表的残留映射：

```c
// kernel/proc.c - growproc 缩容分支
} else if(n < 0){
    uint64 oldsz = sz;
    sz = uvmdealloc(p->pagetable, sz, sz + n);
    
    // 清除内核页表中对应的残留映射
    for(uint64 va = sz; va < oldsz; va += PGSIZE) {
        uvmunmap(p->kernel_pagetable, va, 1, 0); // 不释放物理页（物理页已由 uvmdealloc 释放）
    }
}
```

## 5. 变量和指针的地址：什么时候被存入用户页表？

### ❓ 困惑点
程序里定义 `int a = 5;`，这个 `a` 的地址什么时候被写进页表？

### ✅ 时间线拆解
1. **编译/链接阶段**（程序运行前）：编译器为变量分配**虚拟地址（VA）**（如 `0x1080`），固化在 ELF 文件中。
2. **加载阶段（`exec` 系统调用）**：内核读取 ELF，调用 `uvmalloc` 分配物理页，并在**用户页表**中建立 `VA -> PA` 的映射。
3. **堆分配阶段（`sbrk` / `malloc`）**：程序申请堆内存时，内核调用 `uvmalloc`，在用户页表中建立新堆区的映射。

### 📌 关键结论
用户程序**无权修改页表**，它只是持有虚拟地址。真正的“虚拟→物理”映射，是内核在 `exec` 和 `sbrk` 时主动填入用户页表的。

## 6. 同步时机：哪些地方必须调用 `copy_proc_to_kernel`？

用户页表发生变化的所有时刻，都必须同步到内核页表：

| 触发点 | 变化内容 | 调用位置 |
| :--- | :--- | :--- |
| `userinit` | 创建第一个进程 | 初始化完用户页表后 |
| `fork` | 子进程复制父进程页表（`uvmcopy`） | `uvmcopy` 完成后 |
| `exec` | 加载新程序，重建全新页表 | 替换 `p->pagetable` 后，`return` 前 |
| `growproc` | 堆增长/收缩（`uvmalloc` / `uvmdealloc`） | 修改完用户页表后，更新 `p->sz` 之前 |

### ⚠️ 特别注意（易踩坑）：
在 `growproc` 中，**必须先调用 `copy_proc_to_kernel`，再更新 `p->sz = sz`**。如果顺序反了，`oldsz` 和 `newsz` 相等，导致循环不执行，同步失败。

## 7. 权限位的处理：为什么要去掉 `PTE_U`？

```c
*pte2 &= ~(PTE_U|PTE_W|PTE_X);
```

- **`PTE_U`**：标记该页为“用户态可访问”。如果内核页表中保留 `PTE_U`，RISC-V 的 S-mode（内核态）会拒绝访问该页（硬件限制）。
- **`PTE_W` 和 `PTE_X`**：本实验只要求 `copyin`（读数据），所以去掉写和执行权限可以增加安全性。如果以后优化 `copyout`，需要保留 `PTE_W`。
- **保留 `PTE_R`**：保证内核能读取用户数据。

---

## 8. 地址上限：为什么要检查 `newsz >= PLIC`？

```c
if (newsz >= PLIC) panic("user processes exceed PLIC");
```

- `PLIC` 的起始地址是 `0xC000000`，这是 xv6 内核设备寄存器的起始位置。
- 用户虚拟地址和内核虚拟地址共用同一个虚拟地址空间，如果用户进程超过 `0xC000000`，就会和内核的 PLIC 寄存器区域重叠，造成灾难性的数据覆写。
- 所以必须强制限制用户进程最大不能触及 PLIC 地址。

---

## 🎯 总结：一句话核心

> **实验就是让每个进程的内核页表，成为用户页表的“物理地址镜像”（去掉 PTE_U），保证 `copyin_new` 直接解引用用户虚拟地址时，硬件能正确翻译出物理地址。**

- 同步的是**页表项（映射关系）**，不是数据内容。
- 变化发生在 `exec`、`fork`、`growproc` 等关键点，要及时调用同步函数。
- 缩容时必须主动清除内核页表残留，避免悬空映射漏洞。
- 用户程序的变量地址在编译时确定，但映射关系由内核在加载/分配时动态填入页表。
